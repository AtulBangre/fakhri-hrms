## Instructions

- **Applicability Class** is a starting classification: Core, Conditional, or Feature-Specific. It does not automatically make a check applicable.
- **Applies?**: Yes / No / TBD. Mark No only with evidence-backed justification. Feature-Specific checks apply when that feature is enabled.
- **Status**: Not Tested / Pass / Fail / Partial / N/A / Blocked. N/A requires Applies? = No and a reason. Do not count Blocked or Not Tested as Pass.
- **Priority**: P0 = release-blocking if applicable and failed; P1 = high; P2 = medium. Adjust for actual business impact.
- **Evidence**: Record file:line, config path, screenshot, log ID, test command, and timestamp. Never paste secrets, face images, embeddings or payroll PII.
- **Test Method** is suggested, not evidence of testing. All results below are intentionally blank.

## Critical architecture assumptions to verify

1. SQLite is the operational source of truth for kiosk events, but **entity ownership and cloud sync direction must be explicitly defined**. Supabase is not automatically a backup merely because data is replicated.
2. WAL improves read/write concurrency but **does not guarantee sub-0.1 ms end-to-end kiosk speed**; measure actual p50/p95 including camera, AI inference, API and storage. SQLite still permits one writer at a time.
3. Cloud replication does not replace **tested, point-in-time-capable backups** and reconciliation.
4. Biometric and payroll data require strict privacy, access, retention and incident controls; legal requirements must be validated against current applicable rules.
